# マップチップメタデータ設定ツール仕様

## 位置付け

本書は、ワールド、ダンジョン、町で使用するマップチップについて、画像上の領域と表示、
境界、アニメーション、ランダム差分、通行判定を対応付ける「メタデータ設定ツール」の
仕様を定める。後続のマップエディタは、本ツールが出力したタイルセットメタデータだけを
参照し、画像座標や境界判定を独自に解釈しない。

ワールドマップの最初の対象画像は
`content/images/mapchips/worldmap.png` とする。画像自体は本ツールで編集しない。

本書で定めるのは制作データとツールの振る舞いである。ゲーム実行時の責務分割は
[`program-architecture.md`](../program-architecture.md) を参照する。

## 結論

- 1セルと画像上の1チップは16×16pxで固定する。
- マップの論理データは「地面」と「オブジェクト」の2系統に分ける。
- 地面は親子関係を持つ描画スタックとして定義し、保存時に下層から1セルへ合成する。
- ワールドの地面は `sea`、`plain`、`sand` の3種とし、`sea` だけを通行不可とする。
- 森、湖、山、町、村などはオブジェクトとして定義する。森の占有セルは通行不可とする。
- 山の入口などは前面パーツとして重ね、必要なセルだけ通行可で上書きできる。
- 境界、重み付きランダム、アニメーションは共通の表示定義としてメタデータ化する。
- マップ保存時に境界選択、ランダム選択、地面合成、オブジェクト展開、通行グリッド生成を
  済ませる。ゲーム実行時にはこれらのルールを再評価しない。
- 制作用マップとゲーム用生成物を分ける。ゲーム用生成物は制作データから再生成できるものとし、
  人が直接編集しない。

## 用語

| 用語 | 意味 |
|---|---|
| セル | マップ上の16×16pxの論理位置 |
| ソースチップ | 元画像上の16×16px領域。列・行の0始まり座標で参照する |
| 地面種別 | 各セルが1つだけ持つ `sea`、`plain`、`sand` などの安定ID |
| 地面レイヤー | 地面種別の親子関係から得る描画要素。下層から順に合成する |
| オブジェクト定義 | 森、山、町など、1つ以上のセルと通行設定からなる再利用可能な定義 |
| オブジェクト実体 | マップ上の起点、重なり順、定義IDを持つ配置データ |
| 表示候補 | 重み付きランダムで選ばれる1つの見た目。内部に1枚以上のアニメーションフレームを持てる |
| 制作用データ | 人が編集・レビューする正本 |
| ゲーム用データ | マップ保存時に生成する、描画と通行判定に特化したデータ |

## 対象範囲

### 本ツールで行うこと

- タイルセットID、元画像、対応マップ種別の設定
- 地面種別、描画親、通行可否の設定
- 通常表示、境界表示、アニメーション、重み付きランダム表示の設定
- 複数セルからなるオブジェクトとセル単位の通行可否の設定
- 画像座標、参照、境界ルール、重み、オブジェクト範囲の検証
- 3×3地面プレビュー、アニメーションプレビュー、オブジェクトプレビュー
- バージョン付きJSONの保存

### 本ツールで行わないこと

- 元画像の描画、色修正、切り抜き、パレット変換
- マップ上への地面塗布やオブジェクト配置
- 出入口、イベント、宝箱の開封状態、扉の解錠状態などのゲーム進行設定
- プレイヤー、NPC、敵の配置
- 制作用マップからゲーム用マップへの最終コンパイル

後半4項目は②マップエディタとマップコンパイラの責務とする。ただしコンパイラが必要とする
表示・通行ルールは、本ツールのメタデータで欠落なく表現できなければならない。

## 共通データモデル

### ファイル配置

実装時の正本と生成物は次のように分ける。

```text
content/
├── images/mapchips/                 # 元画像
└── maps/
    ├── tilesets/                    # 本ツールが編集するタイルセットJSON
    └── sources/                     # マップエディタが編集するマップJSON

app/
└── maps/                            # マップコンパイラが生成するゲーム用データ
```

`content/data` はGoogle Sheetsと同期する配列形式のマスターデータであるため、空間データである
タイルセットとマップは置かない。`app/maps` は生成物とし、直接編集しない。

### タイルセット共通属性

タイルセットは最低限、次の属性を持つ。

| 属性 | 内容 |
|---|---|
| `format_version` | メタデータ形式の整数バージョン。profile単数化後は2 |
| `tileset_id` | マップから参照する安定ID |
| `source_image_id` | 画像manifestの安定ID。ワールドは `mapchips/worldmap` |
| `tile_size` | 16固定。異なる値は読み込みエラー |
| `profile` | `world`、`dungeon`、`town` のいずれか1つ |
| `grounds` | 地面種別の定義配列 |
| `objects` | オブジェクト定義配列 |

IDには表示名を使わず、`lower_snake_case` の安定キーを使う。表示名を後から付ける場合も、
ID変更とは別操作にする。

`grounds` の先頭をベース地面とする。ベース地面は親を持たず、タイルセット作成後はIDと
先頭位置を変更できない。タイルセットのprofileも作成後は変更できない。`world` profileの
タイルセットでは、ベース地面IDを `sea` とする。
同じソース画像を別profileで使う場合は、画像を共有する別のタイルセットとして定義する。

### 元画像のグリッド

- 選択可能なソースチップは、左上を原点とする16pxグリッドに完全に収まる領域だけとする。
- 画像寸法が16の倍数でなくても読み込める。右端または下端の16px未満の余白は選択できない。
- 選択不能な余白に透過色以外の画素があれば警告する。メタデータは保存できるが、通常の
  画像ビルドは別途成功させなければならない。
- `worldmap.png` は400×150pxであるため、25列×9行を選択でき、下端6pxは余白として扱う。

### 地面の親子関係と描画

各地面種別は0個または1個の `parent_id` を持つ。セルには最上位の地面種別IDを1つだけ保存し、
表示時は親を根までたどって下層から合成する。

ワールドの初期定義は次の関係とする。

```text
sea（通行不可）
└── plain（通行可）
    └── sand（通行可）
```

たとえば `sand` セルは、海、平地、砂地の表示をこの順に合成する。通行可否は親から継承せず、
セルに保存された最上位地面種別の値を使う。したがって、`plain` が `sea` を描画上の親に持っても
通行不可にはならない。

親子関係を固定enumにしないことで、ダンジョンの奈落→床→敷物、町の水面→地面→舗装路なども
同じ仕組みで定義できる。親の循環と、存在しない親への参照は問題一覧へエラー表示する。

### 表示候補、ランダム差分、アニメーション

通常チップと境界チップの表示は、同じ `visual` 構造を使う。

- `visual` は1つ以上の表示候補を持つ。
- 各表示候補は一意な候補ID、0以上の整数重み、1枚以上のフレームを持つ。候補IDは
  設定ツールが自動で付与する内部値とし、ユーザーの入力対象にしない。
- 重みの合計は1以上とする。重み0は候補を一時的に無効化する用途だけに使う。
- 候補が複数ある場合、マップ保存時に重みに従って1候補を選ぶ。
- 1候補に複数フレームがある場合、`frame_interval` ごとに末尾から先頭へ循環する。
- 静止画は1候補・1フレーム、アニメーションは1候補・複数フレーム、ランダム差分は
  複数候補・各1フレームとして表せる。ランダム選択後にアニメーションする候補も表現できる。
- すべてのフレームは同じ16×16pxとし、ソースチップ座標で指定する。

重み `7, 2, 1` は70%、20%、10%として表示する。パーセント値は確認表示であり、JSONには
整数重みを保存する。

ランダム結果は保存のたびに無関係に変えない。制作用マップが持つ `visual_seed`、マップID、
セル座標、地面レイヤーIDまたはオブジェクト実体IDから決定的に選び、ゲーム用データへ
選択済み候補IDを書き出す。同じ入力の再保存では同じ結果になる。「全体を振り直す」または
選択範囲の「振り直す」をマップエディタで明示した場合だけseedを更新する。

### 境界ルール

境界ルールは中心セルの周囲8方向を、次の3状態で指定する。

| 状態 | 意味 |
|---|---|
| `same` | 隣接セルの描画スタックに、判定中の地面レイヤーが含まれる |
| `different` | 隣接セルの描画スタックに、判定中の地面レイヤーが含まれない |
| `any` | 隣接セルを条件にしない |

方向の正規順序は `n`, `ne`, `e`, `se`, `s`, `sw`, `w`, `nw` とする。中心はルール所有元の
地面レイヤーで固定され、編集対象にしない。

各境界ルールのIDは設定ツールが自動で付与する内部値とし、ユーザーの入力対象にしない。

`same` は最上位地面種別の完全一致ではなく、判定中レイヤーを含むかで判定する。たとえば
`sand` セルは `plain` レイヤーも含むため、平地の境界判定では `plain` セルと `sand` セルは
`same` になる。一方、砂地の境界判定では `plain` セルは `different` になる。これにより、
平地の海岸線を保ったまま、その上へ砂地の境界を合成できる。

マップ外は全レイヤーに対して `different` とみなし、通行判定は不可とする。全profileで
外周をタイルセット先頭のベース地面にすることをマップ検証でも要求し、不意に地面端が
露出することを防ぐ。ワールドのベース地面は `sea` とする。

1つの地面レイヤーで複数ルールが一致した場合は、`boundaries` 配列の先頭から評価し、
最初に一致した1件を採用する。設定ツールではルールを左から右へ並べ、左ほど優先度が高い。
数値の優先度は持たない。

一致する境界ルールがない場合は通常表示を使う。全方向 `any` の境界ルールは通常表示と
同義になるため禁止する。ツールは8方向の全組み合わせを検査し、先行ルールに常に遮られて
決して採用されないルールを保存前に報告する。

### オブジェクト

オブジェクト定義は次を持つ。

- 一意なオブジェクト定義ID
- 幅×高さのフットプリント
- 起点からの相対位置で指定する構成セル
- 構成セルごとの表示定義または明示的な空セル
- 構成セルごとの通行可否
- 既定の描画グループ

起点はフットプリント左上のセルとする。2×2、3×2などを標準的な用途とするが、森の小木、
看板、扉などへ共通形式を使うため1×1も許可する。透明な装飾セル、表示を持たない当たり判定
セルも明示的に定義できる。

マップ上では異なるオブジェクト実体の領域を重ねてよいが、起点座標は同じにできない。
描画グループは通常の `object`、通常オブジェクトより手前の既存の前面パーツ
`object_overlay`、プレイヤーやactorより前面の `object_foreground` を使用する。
`object` と `object_overlay` を描画してからactorを描画し、その後に `object_foreground` を描画する。
各グループ内はオブジェクト下端Y、`order`、起点X、実体IDの順で固定する。
「前面へ」「背面へ」は同じ描画グループと下端Yの実体間で `order` を変更する操作とし、
配列の偶然の並び順には依存しない。

ワールドの森、湖、山、町、村はオブジェクトとして扱う。森の通行不可は、森オブジェクトの
該当構成セルを `blocked` にすることで表す。町や村の入口など、一部だけ進入可能な複合物も
セル単位で設定できる。

### 通行判定

地面の通行設定は従来どおり `passable` / `blocked` の2値とする。オブジェクト構成セルは
次の3状態を持つ。

| 値 | 意味 |
|---|---|
| `passable` | 自身は通行を妨げず、それまでの判定を変更しない |
| `blocked` | そのセルを通行不可にする |
| `passable_override` | そのセルを通行可で上書きする |

ゲーム用の通行グリッドはマップ保存時に次の順で生成する。

1. セルの最上位地面種別が `blocked` なら通行不可にする。
2. オブジェクトを描画順と同じ奥から手前の順に処理する。
3. `passable` は現在値を維持し、`blocked` は通行不可、`passable_override` は通行可へ更新する。

通常の `passable` は下にある `blocked` を解除しない。`object_overlay` の
`passable_override` は下にある山などの不可判定を解除でき、さらに手前のオブジェクトが
あれば、その設定が最終結果となる。
見た目が透明かどうかと通行判定は連動させない。画像の透明画素を調べて当たり判定を推測しない。

将来、船、飛行、浅瀬、移動コストなどが必要に
なった場合は `format_version` を上げ、移動種別ごとの判定へ拡張する。初版から未使用の
汎用タグや式評価を導入しない。

## JSON形式案

以下は形式を示す最小例であり、`worldmap.png` の実際の座標割り当てではない。

```json
{
  "format_version": 2,
  "tileset_id": "worldmap",
  "source_image_id": "mapchips/worldmap",
  "tile_size": 16,
  "profile": "world",
  "grounds": [
    {
      "id": "sea",
      "parent_id": null,
      "collision": "blocked",
      "base_visual": {
        "frame_interval": 30,
        "choices": [
          {
            "id": "default",
            "weight": 1,
            "frames": [{"tile": [0, 0]}, {"tile": [1, 0]}, {"tile": [2, 0]}]
          }
        ]
      },
      "boundaries": []
    },
    {
      "id": "plain",
      "parent_id": "sea",
      "collision": "passable",
      "base_visual": {
        "frame_interval": 1,
        "choices": [
          {"id": "a", "weight": 7, "frames": [{"tile": [3, 1]}]},
          {"id": "b", "weight": 2, "frames": [{"tile": [4, 1]}]},
          {"id": "c", "weight": 1, "frames": [{"tile": [5, 1]}]}
        ]
      },
      "boundaries": [
        {
          "id": "north_edge",
          "neighbors": {
            "n": "different", "ne": "any", "e": "same", "se": "any",
            "s": "same", "sw": "any", "w": "same", "nw": "any"
          },
          "visual": {
            "frame_interval": 1,
            "choices": [
              {"id": "default", "weight": 1, "frames": [{"tile": [0, 1]}]}
            ]
          }
        }
      ]
    }
  ],
  "objects": [
    {
      "id": "forest_2x2",
      "size": [2, 2],
      "default_draw_group": "object",
      "cells": [
        {"offset": [0, 0], "collision": "blocked", "tile": [7, 0]},
        {"offset": [1, 0], "collision": "blocked", "tile": [8, 0]},
        {"offset": [0, 1], "collision": "blocked", "tile": [7, 1]},
        {"offset": [1, 1], "collision": "blocked", "tile": [8, 1]}
      ]
    },
    {
      "id": "mountain_entrance",
      "size": [1, 1],
      "default_draw_group": "object_overlay",
      "cells": [
        {"offset": [0, 0], "collision": "passable_override", "tile": [9, 1]}
      ]
    }
  ]
}
```

オブジェクトセルも地面と同じ `visual` 構造を使用できる。単一静止チップは上例の短縮形
`tile` を許可し、表示候補またはアニメーションを追加した時点で、表示を持つ全構成セルを
`visual` へ正規化する。オブジェクト全体で1つの候補とフレームを選ぶため、各表示セルの
候補ID、重み、フレーム数、`frame_interval` は一致させる。マップ保存時の候補抽選seedは
オブジェクト実体IDまでを共通部分とし、構成セルの相対位置を含めない。

## ツール画面

画面は次の4領域で構成する。具体的なウィンドウ寸法は実装時に決める。

1. ヘッダー: エディタ切り替え、保存状態、Undo/Redo、保存
2. ソース画像: 最近傍拡大、16pxグリッド、パン、ズーム、単一・矩形選択
3. 設定パネル: 基本、地面、境界、オブジェクトの各編集
4. プレビュー／問題一覧: 合成結果、アニメーション、通行表示、エラーと警告

3列表示が可能な広いウィンドウでは、主要な作業領域である中央の設定パネルへ最も多くの
横幅を割り当てる。

ソース画像では使用済みチップを種類別に強調し、選択中の定義から使われる全フレームを
同時に確認できるようにする。同じソースチップを複数定義から参照すること自体は許可する。
選択カーソルは砂地と区別しやすく、マップ素材での使用予定がない透過色に近いピンクで表示する。

### 地面編集

- 地面ID、親地面、通行可否を編集する。
- 表示候補を追加し、各候補の重みとフレーム列を設定する。候補IDは自動設定する。
- 3×3プレビューの各セルへ地面種別を置き、親を含む合成結果を確認する。
- 3×3プレビューの外側は端セルと同じ地面が続くものとして扱い、表示範囲外を理由に
  境界ルールを発動させない。境界は3×3内で設定した地面同士の関係だけで確認する。
- 「通行判定を枠表示」をチェックしたときだけ、通行不可セルを赤枠、通行可上書きセルを
  青緑枠で確認できる。
- 3×3の地面配置、通行判定の枠表示、一時停止の各プレビュー設定は、タイルセットごとに
  ブラウザへ保存し、同じブラウザでの再読み込みやツール再起動後に復元する。
  これらは確認専用の状態であり、タイルセットのメタデータには保存しない。

### 境界編集

- 3×3の中心以外をクリックするたび、`any` → `same` → `different` → `any` と切り替える。
- 境界ルールは先頭フレームを代表画像とする横並びのタブで表示し、左ほど優先とする。
- ルールIDは自動設定し、「左へ」「右へ」で順序を並べ替える。
- 任意の3×3地面配置に対し、どのルールがどの理由で選ばれたか表示する。
- 先行ルールに遮られる到達不能なルール、通常表示へ落ちる組み合わせを一覧できる。
- 回転や反転によるルール自動生成は初版に含めない。必要になった時点で、生成結果を明示的な
  8方向ルールとして保存する補助機能を追加する。

### ランダム・アニメーション確認

- 地面・境界のフレーム列にあるチップをクリックすると、そのフレームをソース画像で
  現在選択中のチップへ置き換える。置換専用の別ボタンは設けない。
- 重みを比率とパーセントの両方で表示する。
- 指定seedによるタイル状サンプルを表示し、偏りと継ぎ目を目視できるようにする。
- サンプル再生成はプレビューだけに作用し、メタデータやマップのseedを変更しない。
- アニメーションはゲームと同じフレーム間隔で再生、一時停止、1フレーム送りができる。
- A→B→C→Aの循環順をサムネイル列で明示する。

### オブジェクト編集

- ソース画像上の矩形選択から幅×高さと構成セルを初期生成できる。
- 地面と同じく表示候補の追加・削除、重み、フレーム列、フレーム間隔を編集できる。
- 2つ目以降の表示候補、フレームの追加、既存フレームの置換には、オブジェクトの幅・高さと
  同じ寸法の矩形選択だけを使用できる。異なる寸法の選択中は追加操作を無効にする。
- 候補抽選とアニメーションの現在フレームはオブジェクト全体で共有し、構成セルごとに別候補を
  選んだり、フレームがずれたりしない。
- 保存済みオブジェクト定義IDを変更した場合は、同じタイルセットを使用する全制作用マップの
  `objects[].definition_id` を同じ保存操作内で追随更新する。Undo/Redo後に保存した場合も、
  最後に保存したIDから現在のIDへの変更として扱う。
- 保存済みオブジェクト定義を削除した場合は、同じタイルセットを使用する全制作用マップから、
  その定義を参照する配置済みオブジェクト実体を同じ保存操作内で削除する。
- 描画グループは「通常オブジェクト」「前面パーツ」「キャラクター前景」から選択する。
- 構成セルの左クリックは従来どおり `blocked` と `passable` を切り替える。
- 構成セルの右クリックは `passable_override` と `passable` を切り替え、ブラウザの
  コンテキストメニューは表示しない。
- 初期生成後に構成セル単位で使用チップを置き換えたり、セルを削除したりする操作は設けない。
  使用チップと構成範囲を変更する場合は、ソース画像上の矩形選択からオブジェクト全体を作り直す。
- 起点を左上マーカーで表示する。
- オブジェクト単体の表示と、3状態の通行設定を確認する。
- フットプリント外のセル、同じ相対座標の重複、幅または高さ0は問題一覧へエラー表示する。

## 保存と検証

- 保存は検証エラーの有無にかかわらず、一時ファイルへ完全なJSONを書いてから置き換える。
  問題一覧のエラーは保存後も残し、後続の編集で修正できるようにする。
- オブジェクト定義IDの変更に伴う制作用マップの更新も保存前に検証し、更新対象マップの書き込みに
  失敗した場合は書き込み済みの対象マップを変更前へ戻して、タイルセットを置き換えない。
- オブジェクト定義の削除に伴う配置済み実体の削除も、タイルセット保存と同じトランザクションで
  行う。途中の書き込みに失敗した場合は更新済みマップを変更前へ戻す。
- JSONルートがobjectでない、または安全な保存先を特定できるタイルセットIDがない場合だけは
  ファイルへ保存できないため保存失敗とする。
- キー順、配列順、インデントを固定し、値を変更していない保存で差分を発生させない。
- 未保存変更がある状態でファイル切り替えまたは終了を行う場合は確認する。
- Undo/Redoは最後の保存後も、同じ起動中は編集単位で保持する。
- 読み込み時に未知の `format_version` を黙って書き換えない。
- 問題一覧は編集のたびに自動更新し、独立した検証ボタンは設けない。保存時にも同じvalidatorを使う。

ヘッダーから既存タイルセットを切り替え、新しいタイルセットを作成できる。複数のタイルセットで
同じ `source_image_id` を選択してよい。ソース画像はタイルセット作成時に決定し、作成後は変更できない。
別の画像を使う場合は新しいタイルセットを作成し、マップエディタ側でマップに紐づくタイルセットを
変更する。

タイルセットは確認後に削除できる。ただし、使用中のマップが1件でもあるタイルセットと、ゲームの
必須タイルセットである `worldmap` は削除できない。タイルセットを削除してもソース画像は削除しない。

問題一覧へエラー表示する項目（エラー表示中も保存可能）:

- 必須IDの空、形式違反、重複
- `world`、`dungeon`、`town` 以外のprofile、または作成済みタイルセットのprofile・ソース画像変更
- 元画像または画像manifest IDの不在
- 親地面の不在または循環
- 画像の選択可能範囲外を指すフレーム
- すべての候補重みが0、負数、小数、フレームなし
- アニメーションに対する0以下のフレーム間隔
- 全方向 `any` の境界ルール
- オブジェクトの不正な寸法、範囲外セル、重複セル
- `world` profileで `sea`、`plain`、`sand` または所定の通行設定が欠ける状態

警告にする項目:

- 元画像のパレット外色、半透明画素、選択不能な余白の非透過画素
- `world` profileで平地・砂地の境界ルールまたはオブジェクト定義がまだない状態
- どの入力でも採用されない境界ルール
- どの定義からも参照されないソースチップ
- 同じソースチップの複数用途での参照
- 通行不可だが表示のないオブジェクトセル

## マップ保存時のコンパイル契約

②マップエディタは保存時に、制作用マップの書き込みとゲーム用マップ生成を1操作として実行する。
ゲーム用生成に失敗した場合は直前のゲーム用生成物を置き換えず、保存結果を「ゲームで利用可能」
として扱わない。

マップコンパイラは次を事前解決する。

1. 地面種別の親子スタック
2. 各レイヤーの8方向境界ルール
3. 重み付き表示候補
4. 下層からの16×16px地面合成と、同一結果の重複排除
5. オブジェクト定義の構成セル展開と描画順
6. 静的表示用タイルマップまたは描画面
7. アニメーション更新対象の座標、周期、選択済みフレーム列
8. セル単位の通行可否グリッド

ゲーム実行時は、静的な地面をまとめて描画し、周期が到来したアニメーション対象だけを
事前生成済みフレームへ差し替える。境界探索、乱数抽選、透過合成、オブジェクト定義の展開、
通行判定の合成は行わない。

ゲーム用データの物理形式は、最初のマップコンパイラ実装時に実測してJSON、バイナリ、Pyxel
Tilemapのいずれかを決める。ただし制作用JSONとは分離し、安定ID、形式バージョン、元データの
ハッシュを持たせる。この選択で本書のタイルセット形式を変更しない。

## ワールド以外への適用

共通化するもの:

- 16×16pxセル
- 地面の親子スタックと境界判定
- 表示候補、重み、アニメーション
- 複数セルオブジェクト、重なり順、セル単位の通行判定
- 制作用データとゲーム用生成物の分離

マップprofileごとに追加するもの:

| profile | 後続設計で扱う固有事項 |
|---|---|
| `world` | 外周海、町・村への進入点、ワールド移動、エンカウントなし |
| `dungeon` | 洞窟、森などの屋外戦闘マップ。初版では固有ギミックを扱わない |
| `town` | 町・村などの集落。建物、屋根や前景、NPC、施設イベント、前後関係 |

扉や宝箱のような状態変化する物体は、タイルセット側では状態ごとのオブジェクト定義を用意し、
どの状態を表示するかはマップイベントまたはSaveDataが決める。メタデータへイベント式や
SaveData参照を直接埋め込まない。

町やダンジョンでプレイヤーの前後にまたがる描画が必要になった場合も、論理系統は地面と
オブジェクトの2つのまま保つ。オブジェクト実体の描画グループを背景、Yソート、前景などへ
拡張し、第三の論理マップデータを増やさない。

## 実装分割案

```text
tools/mapchip_metadata/              # 対話UIと編集中状態
scripts/map_pipeline/                # JSON Schema、検証、合成、コンパイル
app/resources/maps.py                # ゲーム用生成物の読み込みと形式検証
app/rendering/map_renderer.py        # 解決済み表示データの描画
```

対話UIは制作データを編集するだけとし、検証器とコンパイラを独自実装しない。マップエディタと
CIも `scripts/map_pipeline` の同じ検証・コンパイル処理を使う。ゲーム側は制作JSONやPNGを
直接読まず、`app/maps` の生成物だけを読む。

対話UIは、loopbackだけで待ち受けるローカルWeb UIとする。起動ごとに一時tokenを発行し、
保存・検証APIはtokenが一致するリクエストだけを受け付ける。以前の起動時から残っている
同一オリジンのツール画面は、UI専用ヘッダーを要求するセッション更新APIで現在のtokenを
再取得し、失敗した操作を一度だけ自動再試行する。これにより編集中データを失わず再接続する。
データモデルと検証器は
UIから独立したPythonモジュールとし、後続のマップエディタからも利用する。

## 受け入れ条件

- 400×150pxの `worldmap.png` を25列×9行の選択可能グリッドと下端6px余白として開ける。
- `sea` → `plain` → `sand` の親子関係と、海だけ通行不可の設定を保存できる。
- 8方向を `same` / `different` / `any` で設定し、3×3プレビューで採用ルールを確認できる。
- A→B→C→Aのアニメーションと、重み7:2:1のランダム候補を設定・確認できる。
- 同じ幅・高さのチップ群をオブジェクトの表示候補として複数設定でき、異なる寸法の候補追加を
  拒否できる。選択された候補とアニメーションフレームはオブジェクト全体で一致する。
- 同じ制作マップとseedからは、保存回数にかかわらず同じランダム結果を生成できる。
- 2×2、3×2、1×1のオブジェクトを作成し、セルごとの通行可否を設定できる。
- 前面パーツと `passable_override` を設定し、通常オブジェクトの通行不可を解除できる。
- 配置済みのオブジェクト定義IDを変更すると、同じタイルセットを使う全マップの参照IDも更新される。
- キャラクター前景を設定し、通行可能な屋根などをプレイヤーやactorより手前へ表示できる。
- 同一起点を拒否しつつ、異なる起点のオブジェクト重複と決定的な描画順を扱える。
- 地面が通行可能でも、重なるオブジェクトの該当セルが通行不可なら生成済み判定も不可になる。
- 到達不能な境界ルール、範囲外チップ、親循環、不正重みを保存前に検出できる。
- ゲーム用データの描画・通行時に、境界判定、乱数抽選、地面レイヤー合成を行わない。
- `world` 固有IDをコード全体のenumにせず、別タイルセットで `dungeon` と `town` を定義できる。

## 素材上の透過色

`worldmap.png` の背景はZEROの画像パイプラインで予約しているパレット番号1の `#FF0080` とする。
メタデータツールではこの色を常に透明表示し、ゲーム用画像ビルドでも透過色として扱う。
画像のパレット不一致はメタデータ保存では警告とし、`images:build` ではエラーとする。

## 実装と確認

- 共通起動・ルーティング: `tools/editor/` の `/tileset/`
- 対話UI・ローカルAPI: `tools/mapchip_metadata/`
- メタデータモデル・検証: `scripts/map_pipeline/tileset.py`

```sh
npm run tools:editor -- --editor tileset
npm run tools:mapchip-metadata
npm run maps:validate
```

`tools:mapchip-metadata` は同じ統合エディタをマップチップ画面から開く互換入口である。ヘッダーから
マップ、イベントへ切り替えられ、保存・検証は従来どおり本ツール固有のApplicationが処理する。
